## 3. Брендинг и дефолты форка

**Ничего не откатилось, потому что брендинг в коде кабинета не живёт вовсе.**

* `index.html` содержит плейсхолдер `__APP_NAME__`; его на сборке подставляет
  `vite-plugins/brandingHtml` из `VITE_APP_NAME` (пусто → `Cabinet`), а реальное имя
  «Дон Батон» кабинет получает **в рантайме** запросом `GET /cabinet/branding` к боту —
  инлайновый скрипт в `<head>` ставит `document.title` и меты ярлыков ещё до бандла.
  Фавикон — статическая ссылка на `/cabinet/branding/favicon` у бота.
* `__API_URL__` подставляется из `VITE_API_URL`, дефолт `/api` — ровно то, что у нас в проде.
  Поэтому `stage-cabinet.sh`, который зовёт голый `npm run build` без build-args, даёт
  корректный для прода бандл: имя и логотип приезжают от бота, адрес API совпадает с дефолтом.
* Апстрим 1.77.0 ни `index.html` в части бренда, ни `brandingHtml`, ни `documentBranding.ts`
  не менял — добавил в `index.html` только два блока про `color-scheme`, инлайновый
  брендинг-скрипт остался нетронутым.

Наши дефолты (`wifi_lte` первой вкладкой и по умолчанию, тексты `subscription.network`,
подписи периодов) — счётчики выше, всё на месте.

## 4. Требования к боту / backend-API

Бот в проде — **v4.12.1** (выкачен 16.09). Апстрим помечает кабинет 1.77.0 как
«Требует Bot v4.13.0+». Требование конкретное и **целиком** сводится к трём параметрам
ручки `GET /cabinet/admin/users`:

| Что нужно кабинету 1.77.0 | Где в кабинете | Есть в боте 4.12.1? | Появилось в боте |
| --- | --- | --- | --- |
| `sort_order=asc\|desc` | `usersListState.ts` → `buildUsersQuery` | **нет** (параметр не объявлен) | v4.13.0, `admin_users.py:507` + `SortOrderEnum` |
| `sort_by=grace_until` | сегмент «В грейсе» | **нет** (`SortByEnum` без этого члена) | v4.13.0, `schemas/users.py` |
| `in_grace=true` | сегмент «В грейсе» | **нет** (параметр не объявлен) | v4.13.0, `admin_users.py:505` |

Больше кабинет 1.77.0 от бота ничего нового не хочет: единственный изменившийся файл в
`src/api/` — `adminUsers.ts`, и в нём ровно эти три поля.

### Что сломается, если кабинет 1.77.0 окажется в бою раньше бота 4.13.0

Сценарии ранжированы по опасности:

1. **🔴 Сегмент «В грейсе» — 422, список пустой.** Кнопка сегмента шлёт
   `in_grace=true&sort_by=grace_until`. Неизвестный `in_grace` FastAPI просто проигнорирует,
   а вот `sort_by=grace_until` не пройдёт валидацию `SortByEnum` бота 4.12.1 → **422
   Unprocessable Entity** на весь запрос. Админ увидит ошибку загрузки / пустую ленту.
   Данные при этом в безопасности: это `GET`, ничего не пишется.
2. **🟡 Переключатель направления сортировки врёт молча.** `sort_order` старый бот не знает
   и (по умолчанию FastAPI) **игнорирует лишние query-параметры без ошибки**. Кабинет
   покажет в меню «Сначала старые», а список придёт в привычном порядке — без всякого
   признака, что запрос не сработал. Это неприятнее 422: ошибки нет, доверие к экрану есть,
   а сортировка не та.
3. **🟢 Всё остальное работает.** Прочие сегменты, фильтры, поиск, карточка пользователя,
   вкладка GEO, grace-доступ, тарифы — на 4.12.1 без изменений.
4. **🟢 Клиентская часть не деградирует вообще.** Вход (включая deep-link с реф-кодом),
   покупка, смена тарифа, продление, подарок, докупка LTE, экран подписки — новых ручек
   и полей в 1.77.0 не получили. Правки `color-scheme` / подложки Telegram живут целиком
   в браузере.

**Вывод: порядок выкладки — бот 4.13.0, потом кабинет 1.77.0.** Обратный порядок не
катастрофичен (ломается один админский сегмент и врёт один переключатель, клиенты не
затронуты), но он даёт неверные данные админу без явной ошибки, а это худший вид поломки.

### Требования форка к нашему боту не изменились

Ничего нового в этом слиянии не появилось: `network_category` / `lte_quota` /
`lte_traffic_limit_gb` / `lte_period_days`, `request_id` + `expected_price_kopeks` у

## 5. Web app manifest / «кабинет как приложение на Android»

**Требований к nginx и статик-раздаче кабинета нет. Новых путей, файлов и заголовков не нужно.**

Разбор, потому что название фичи вводит в заблуждение:

* Фича живёт **в боте 4.13.0**, а не в кабинете. Бот добавил в `app/cabinet/routes/branding.py`
  (+157 строк) две ручки: `GET /cabinet/branding/manifest.webmanifest?base=<путь>`
  (отдаёт `application/manifest+json`, имя и цвета из брендинга, `display: standalone`,
  `Cache-Control: public`, `Vary: Origin`, `X-Content-Type-Options: nosniff`) и
  `GET /cabinet/branding/app-icon/{size}.png` + `…/app-icon/maskable/{size}.png`.
* **Кабинет 1.77.0 эти ручки не зовёт.** Во всём дереве кабинета нет ни одного упоминания
  `manifest.webmanifest` или `app-icon` — проверено grep'ом по `src`, `index.html`,
  `vite.config.ts`, `vite-plugins`, `nginx.conf`, `Dockerfile`. В дифф `v1.76.1..v1.77.0`
  слово `manifest` не входит вообще.
* Кабинет по-прежнему собирает манифест **сам, на клиенте**: `src/utils/documentBranding.ts`
  (`buildWebManifest` / `setWebManifest`, появилось ещё в `1ca7e489`) вешает
  `<link rel="manifest" href="data:application/manifest+json,…">` с иконками, отрисованными
  локально. Так и остаётся в 1.77.0.
* 🟡 **Практическое следствие:** Chrome на Android не считает `data:`-манифест основанием для
  установки приложения. Ровно поэтому бот и завёл манифест по настоящему адресу — но
  переключение `<link rel="manifest">` на адрес бота должно приехать **следующим** релизом
  кабинета (на 17.09 `v1.77.0` — вершина `upstream/main`, ничего новее нет). То есть
  **после выкладки 1.77.0 «кабинет ставится как приложение на Android» ещё не заработает**;
  серверная половина фичи в боте будет лежать без потребителя. Это не поломка, а
  несостыковка ожиданий от формулировки релиза — владельцу лучше сказать заранее.
* Когда кабинет начнёт звать эти ручки, инфраструктуре всё равно ничего делать не придётся:
  адрес лежит под `/cabinet/branding/…`, то есть под тем же API-префиксом, который уже
  проксируется; `Content-Type` ставит сам бот.
